Halloween Store: free checkout via a client-supplied state key

Intigriti monthly CTF 1026 · October 2026 · solved in ~4.5h · write-up published after the challenge closed · repro: ctf-1026-repro.sh

TL;DR

The challenge was a small shop with one win condition: order The Midnight Collection, a €666.00 product, from a session holding €66.00 of store credit. Checkout is gated server-side, and a successful vault order's receipt carries the challenge token. The duplicate-coupon guard on POST /api/cart/coupon validated the request only as long as it looked exactly like the shipped client's requests. When I added one extra key the client never sends, the guard stopped rejecting an already-applied code, and each promo record's discount could be re-applied. Doubling the two discoverable codes (20% + 30%) stacked the discount to exactly 100% and the €666.00 order checked out at €0.00. The challenge token is withheld on this site by design.

The target

"Halloween Store": a session-scoped shop with no login and no accounts, so the session cookie is the whole game. Checkout is enforced server-side against the credit limit: the total must sit at or under the session credit, and the server answers insufficient_credit otherwise. No client-side check matters, because the server recomputes the total.

Buying the vault means cutting the total by at least 90.09%. Two discount codes exist and both are findable by walking the UI:

  • NIGHT20: 20% off the vault, shown on the product banner.
  • NEWS30: 30%, handed out by POSTing a valid email to /api/newsletter (first-order code).

Applied normally they stack additively: 20% + 30% = 50%, total €333.00. Still five times over the credit. The gap between what the client can reach and what the server accepts is the puzzle.

Step 1: map the surface before touching it

The live API surface is exactly eight endpoints: /api/session, /api/products, /api/cart, /api/cart/items, /api/cart/coupon, /api/cart/coupon/remove, /api/checkout, /api/newsletter. I probed for hidden orders, receipts, coupons, config and admin routes and hit none. When the live surface matches the shipped client's own calls one to one, hidden-route hunting is the wrong lane: the vulnerability has to live in the contract of the found endpoints, in their gates, dedupe rules and stacking math.

The next step was learning what the server recomputes on its own. I verified:

  • percent/amount values injected into a promotion record are dropped and recomputed
  • body fields on /api/cart/items (price, item_price, chosen_discount) are ignored, quantity clamps to >= 1
  • /api/checkout ignores every total/credit/canCheckout/promotions field in its body
  • one vault per session (second add answers already_in_cart)
  • a control order for an €8.90 product returns a receipt with no token field, confirming the win state is tied to the vault order

Everything re-derives server-side except the one rule I had not exercised yet.

Step 2: the duplicate-coupon guard

Re-applying a code behaves correctly: a second POST /api/cart/coupon with the same code answers coupon_already_applied ("Coupon already applied."). The shipped /static/js/app.js sends exactly {"code":"..."} and nothing else. But the cart UI renders each promotion record with its own count, which tells you the server keeps a count field per promotion, and nothing in the UI bounds it.

The probe was one extra key in the coupon body, an empty promotions array, a field the shipped client never sends:

{"code":"NIGHT20","promotions":[]}

No duplicate error. The response says "20% promotion applied." and the server's record becomes count 2, amount 26,640: 20% of €666.00, twice. The duplicate-coupon check stops blocking the already-applied code when the request body carries a promotions key. The same probe with NEWS30 gives count 2, amount 39,960. Combined: 66,600 off a 66,600 subtotal, exactly 100%, total €0.00, and canCheckout flips to true.

In my testing each code's count incremented once, reaching two, which is all this solve needed. Nothing in what I observed ties count to 1 and the discount math extends per record, so the same primitive reaches further wherever promo values allow.

The finding, in one sentence. A client-supplied state key changed which branch a server-side check took. The request carried the same coupon code; only the presence of the extra key distinguished a rejected re-application from an accepted one.

7POST /api/checkout {}receipt: paid €0.00, token inside

Steps 5 and 6 are the vulnerability. Both re-apply a code the duplicate guard should reject, and each increments that promotion's count.

Two receipts, one token

I captured the receipt twice, once through the browser session and once by rebuilding the whole chain from a clean session with a scripted curl client only. Two different order ids, same token. The token value is withheld on this site:

{"ok":true,"receipt":{"paid":0,"credit":6600,
"message":"Your order is confirmed and being prepared.",
"flag":"INTIGRITI{...}"}}

paid: 0 on a €666.00 product. A control order for the €8.90 product returned a receipt with no flag field, confirming the win state is specific to the vault order.

Dead ends I did not bother re-testing after the first pass: the newsletter code is static, so alternate emails or type confusion buy nothing; near-duplicate codes (leading/trailing space, case) still dedupe, so normalization was not the fault; the vault item itself rejects duplicate adds; and the checkout endpoint trusts nothing in its body.

What I'd tell the developer

  • On the coupon-apply endpoint, ignore any client-supplied promotions key entirely: the canonical applied-promotions list is server-side session state.
  • Enforce the duplicate check after normalizing the request code, regardless of any extra body keys.
  • Cap each promotion record's count at 1 and reject discount sums above 100%.

What I'd tell past-me

1. Diff request shapes against the accepted contract. Fields the client never sends but the server still reads are a first-class bypass surface.

2. When the live API surface equals the client's own call list, stop hunting hidden routes. Attack the found endpoints' edge logic: the gates, the dedupe rules, the stacking math.

3. Assume every number is recomputed server-side until proven otherwise. Then spend the effort on the one surface that still trusts the client.

4. Stop and bank. The moment a state-mutating probe succeeds, halt the script and record the winning state before any cleanup step dismantles it.

5. Shared infrastructure leaks other players' guesses. The challenge sat behind a shared proxy pool; foreign request bodies occasionally desynced into my connections as malformed-request dumps. Forcing HTTP/1.1 with Connection: close, retrying on malformed responses, and treating leaked foreign payloads as other researchers' guesses rather than field-name discovery kept the session clean.
